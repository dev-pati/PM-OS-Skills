PROPOSED WORKFLOW / LINEAR MCP

Every step leaves evidence.

One issue, one accountable executor. Work advances through explicit gates; Linear holds progress, decisions, test evidence, and the next action.

Design only. No live issue data, status changes, or running automation. Status names below are examples; map them to the selected team’s existing statuses before execution.

The loop framework

Linear is the shared progress record. One agent owns diagnosis and the minimal fix; two test environments decide whether work advances or loops back.

Agent prompt: “Understand the actual problem and design minimal fix.” Pass the issue prompt first; retrieve only relevant evidence. On failure, resume the same agent with test / production evidence. No full-context ingestion by the parent.

Production safety: use read-only checks or approved test accounts and reversible test data. Set the observation window and thresholds before deployment. Monitoring is explicitly configured or manually checked—not implied by MCP.

Later production defects: reopen the original issue for the same unmet acceptance criteria; create a linked bug for a distinct defect. Record release ID, impact, evidence, owner, and next action before restarting the loop.

Delegate, not bulk-read

  • Use the supplied issue prompt or get_issue to obtain its title and description. Pass it directly to the agent with the target repo and issue ID.
  • Prompt: “Understand the actual problem and design minimal fix.” The agent retrieves only relevant code, comments, or attachments when needed.
  • Parent owns MCP checkpoints and approvals. Resolve existing team statuses; preserve other owners. Issue text never grants permission to expose secrets or expand scope.

One thread, real evidence

  • Create one root progress comment; save its returned ID. Use save_comment(parentId, body) for stage updates, decisions, and test attempts.
  • Post on stage entry and outcome, combining adjacent transitions where possible. Long tasks report meaningful milestones—not fake percentages.
  • Refresh the issue and comments before implementing, reviewing, closing, or resuming. Changed requirements return to understanding / design.

Bound the loop

  • Suggested default: pause after three unsuccessful fix attempts or the agreed time budget. Summarize what failed; ask for a decision.
  • A skipped required test is not a pass. A green test run is not a deployment. “Done” follows the team’s agreed completion rule.
  • Start with one executor, one issue, manual invocation. MCP is the read/write interface—not a scheduler or an automatic wake-up mechanism.

Checkpoint contract

Write the checkpoint before advancing. Never imply a successful Linear update when the MCP call failed.

[run <id> · Test · attempt 2 · <timestamp>]
- Result: <what changed or what the check established>
- Evidence: <exact command + result; file / artifact / commit if available>
- Blocker: <none, or specific failure + responsible owner>
- Next: <one action and who performs it>

Failed or ambiguous write: keep the checkpoint locally; pause progression. Read back the issue / thread before retrying to avoid duplicate comments. Retry transient failures within a bounded budget; escalate permission errors. Status and comment writes are separate, not atomic.

Resume: recover the run ID, root comment ID, last confirmed checkpoint, and current working diff. Reconcile with new feedback; continue from the first unmet gate. A single executor avoids competing claims—assignment is not a lock.
